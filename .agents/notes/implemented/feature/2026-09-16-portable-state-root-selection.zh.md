# Agent Note: Portable state-root selection

Status: implemented

[English](2026-09-16-portable-state-root-selection.md) | 中文

## Problem

[便携启动器](../architecture/2026-09-13-portable-launcher-and-state-location.zh.md)会从 `PortableData/launcher.json` 解析状态目录并在表头呈现结果，但界面中没有任何入口能写入该文件。这个值只能靠手工编辑介质上的文件才能设置。

这个选择有三部分早已建好却无人调用：`resolveStateRoot` 会拒绝不可用的位置，`writeLauncherSettings` 能持久化取值，双语字典备好了四条拒绝理由，却没有任何代码路径能打印它们。随发行版附带的 `Docs/zh-CN/` 中文指南已经描述了从菜单选择该目录，也就是说已交付的产品写着菜单并未提供的入口。

## Decision

菜单新增第五项 `5) 设置状态目录`，位于完整性检查与退出之间。选中后提示输入一个路径，应用该选择，并打印一行结果。

`launcherSettingsPath()` 负责各模式下写入位置，`applyStateRootChoice()` 负责读取已保存设置、解析输入值、写入被接受的取值，并计算下次启动将使用的目录。它返回设置路径、新的目录，以及发生拒绝时的拒绝原因——从不返回只应用了一半的选择。

空行会清除已保存的选择，使两个目录都回到该模式的默认值。其他任何取值都会先解析再保存：被拒绝的值会被报告且不写入任何地方，因为设置文件只应保存启动器能用的选择。取值按用户输入的拼写保存，因此相对路径在介质换到另一个盘符时仍指向同一位置。

被拒绝的取值不会改动已保存的选择，表头继续显示下次启动将使用的目录。`STATE_ROOT_REASON` 把每个 `StateRootDefect` 映射到消息键且只映射一次，`main.ts` 的启动路径与菜单项都经它报告，因此同一个不可用目录无论是被输入还是从文件中读回，都会以同样的话被拒绝。

## Alternatives considered

**打印设置文件路径让用户自己编辑。** 这正是启动器此前的做法，它要求买家知道 Harness home 是什么、文件在哪里、以及启动器拒绝哪些位置。一次被拒绝的手工编辑只会在下次启动时产生一行回退提示，而不说明该改什么。

**接受任何可写目录。** 那三条拒绝之所以存在，是因为每一条都会破坏或危及用户数据：磁盘根会让产品占有一整块盘，包含程序的取值会把程序放进用户数据内部，位于程序目录内部的取值会被卸载删除。只检查可写性会同时接受这三种情况。

**保存解析后的绝对路径而非用户输入的拼写。** 解析后的路径就是启动实际使用的路径，保存它看起来少了一步。它破坏了该设置存在的唯一理由：一块在一台机器上挂载为 `E:`、在另一台上挂载为 `F:` 的介质会保留一个已无法解析的路径，而回退逻辑会静默丢弃用户的选择。

**反复提示直到取值被接受。** 只想查看当前设置的用户将不得不满足规则，或以结束输入的方式离开该项。报告拒绝并返回菜单让每个入口都可退出。

**增加一个同时编辑其他启动器状态的设置入口。** 启动器只保存一个选择。为单个字段提供设置界面会多出一层导航和一个永远为空的第二个字段。

## Consequences

菜单现在提供六项，顺序由 `renderMenu` 决定；该项位于第五，因此 `0) 退出` 保持在最后，也不会有更早的编号在不同构建之间改变含义。

该选择在下次启动时生效。在应用运行期间修改它不会移动该应用的状态，因此确认信息会写出设置文件，并说明下次启动生效，而不是只写出目录。

已无法解析的保存值仍会按既有的 `settings.stateRootRejected` 行回退到模式默认值，因为启动路径未变。菜单项现在是唯一的写入者，因此该回退在同一界面里有了可见的起因和可见的补救方式。

启动器的写入面增加了一个它本就拥有的文件和一个它本就创建的目录。它仍然不启动任何用户可指定的命令，也仍然拒绝那种会让卸载触及用户数据的状态目录。
