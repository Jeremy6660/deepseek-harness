# Agent Note：便携启动器与便携状态的位置

Status: implemented

[English](2026-09-13-portable-launcher-and-state-location.md) | 中文

## 问题

[便携智能体实验盘产品](../../proposed/feature/2026-09-11-portable-agent-usb-product.zh.md)交付的介质，预期由普通 Windows 用户直接打开而不安装任何东西；而[元数据与载体笔记](2026-09-11-portable-product-metadata-and-sea-carrier.zh.md)只留下了打包好的 Runtime，没有给消费者任何入口。在启动器出现之前，必须先回答三个问题。

第一，用什么技术来呈现产品。候选载体此前已经比较过，但“哪个可执行文件承载 Runtime”和“买家最先看到什么”是两个约束不同的决定：启动器必须能在没有 Node.js、没有 Python 的机器上运行，必须不依赖载体笔记已经否决的 Electron 壳，也不能变成与 [`dsh` CLI 的 profile 启动](2026-08-22-single-dsh-application-launcher.zh.md)相互竞争的第二应用入口。

第二，各模式下应用状态放在哪里。提案区分了程序文件所有权与用户状态所有权，并写明免安装模式使用介质自有的 Harness home，但没有说明工作目录与这个 home 的关系，也没有说明已安装产品把状态放在哪里。

第三，状态目录如何选择与告知。买家先用介质运行、再安装产品、之后又想把会话放到别处时，需要一条在所有模式下都成立、并且在任何东西启动之前就可见的规则。

## 决定

`Launcher.exe` 是一个控制台应用，通过与 Runtime 相同的固定 `@yao-pkg/pkg --sea` 载体构建为 Node 单文件可执行程序，呈现的是编号菜单而不是图形外壳。

**一个载体，一条打包路径。** 启动器把 `apps/portable/src/launcher/main.ts` 打包成单个模块，并用固定的 `node24-win-x64` 目标打包。因此一份发行版只有一种打包机制、一组版本固定值和一个 `--skip-build` 逃生口；`build:portable-launcher` 与 `build:portable-runtime` 一样记录自己的输入。启动器不需要 ripgrep sidecar，所以它的记录只列出一个文件。

**身份内联，绝不读取。** 启动器呈现的产品值，来自构建期经同一个 `client-env` 桥梁内联的 `DSH_CLIENT_*` 字符串，而该桥梁也是品牌化客户端构建所消费的。它在运行时不打开任何元数据文件。这正是[元数据与载体笔记](2026-09-11-portable-product-metadata-and-sea-carrier.zh.md)封闭的边界；启动器不重开它，验收样机把 `product.yml` 移出发行目录后仍能跑出菜单，以此证明这一点。

**启动器只启动一个应用，不启动任何命令。** 可执行文件来自发行布局，profile 是随发行版附带的 `consumer` 组合，参数固定为 `--profile consumer --no-open --port 0`。浏览器交接只经一种固定外壳机制，且启动器唯一愿意打开的 URL 是 `http://127.0.0.1/` 根 URL，且必须恰好携带一个 base64url `token` 参数——该判断由启动器自行完成，而不是信任子进程输出。交接失败属于信息披露而非运行失败，因为 URL 已经显示在屏幕上。

**免安装状态是介质上的一对同级目录，已安装状态是 Harness 自己的 home。** 免安装模式把 `PortableData/home` 与 `PortableData/workspace` 并排放置，清单对两者都不拥有，用户的工作随介质移动。已安装模式使用 Harness 的每用户 home，并把工作目录放在其中的 `home/workspace`。这种不对称是刻意的：在介质上，工作目录是买家能在文件管理器里紧挨程序看到的地方；而已安装产品没有这种天然的邻居，`~/.dsh` 则是 Harness 已经为自己定义的位置。

**全部足迹留在介质上。** 单文件载体首次使用时解包原生载荷——数十兆字节的 FFI 与图像库。不加干预时它会解包到操作者配置文件中。启动器把 `PKG_NATIVE_CACHE_PATH` 与 `NARB_NATIVE_CACHE_DIR` 指向 `home/native-cache`，因此免安装运行写入的最大一块东西留在介质上。这一点是测出来的，不是推出来的：首次验收运行报告了介质之外的 17 个文件、20 MB，全部是载体解包产物。

**状态目录因三种位置被拒绝。** 整盘根目录会让产品拥有整个磁盘。包含或等于程序目录的值会让程序落在用户数据内部。位于程序目录内部的值会在程序消失时一并被删——而卸载正是如此——但在介质上 `PortableData` 之下例外，因为清单从不拥有它，且介质自带的默认 home 就在那里。被拒绝的目录回退到该模式默认值并说明原因，因为在默认位置启动总好过不启动。

**存储的目录保留用户输入的拼写。** 相对值相对发行根目录解析，因此在一台机器上写下的选择，在介质以另一个盘符挂载时仍指向同一位置。

## 考虑过的替代方案

**用 Electron 桌面壳作为启动器。** 载体笔记已经基于实测否决 Desktop 作为产品壳：616 MB、11,734 个文件，对 246 MB、2 个文件。重新引入 Electron 的启动器会把载体决定所移除的体积、文件数和更新面全部请回来。

**直接面向操作系统编写图形启动器。** 原生窗口能让启动器更醒目地展示 logo 与品牌色，但它会给这个“发行构建刻意只有一条打包路径”的仓库引入第二套工具链，并且会让启动器自身的界面——而不是一小组字符串——成为需要本地化、主题化和测试的对象。

**让启动器在运行时读取 `product.yml`。** 这样发布方在写好的介质上改文件即可，无需重新构建。但它重开了上一个里程碑刻意封闭的边界：已校验的内联字符串是消费侧唯一可信任的产品值，而用户可以在可执行文件旁编辑的文件，恰恰是这条边界要排除的输入。

**让启动器在首次运行时构建 Runtime。** 载体笔记已否决，理由与此处相同：普通启动会依赖完整的编译器与包管理器环境，干净机器的承诺会退化成一套安装流程。

**两种模式都把工作目录放进 Harness home。** 这样统一，只有一条规则而不是两条。代价是买家无法在不了解 Harness home 是什么的情况下，从文件管理器里看到并使用自己的项目文件夹；而且 `PortableData/home` 会成为寻找用户自建工作的唯一去处。

**免安装模式保留载体默认的原生缓存位置。** 这是载体的默认行为，也能正常工作。否决理由是：它让一次介质运行把最大的足迹留在一台买家未必拥有的主机上，而且换一台机器就要把第一台机器已解包的东西全部再解包一遍。

**任何情况下都拒绝位于发行根目录内部的状态目录。** 更易陈述，也是最初的实现。但它会在用户照抄介质自带默认 home 时拒绝该目录，这是自相矛盾的；而且它拒绝了介质内部唯一一个清单已声明为用户所有的目录。

**把选定的状态目录存在操作系统而不是介质上。** 注册表跟随的是人，不是产品。被指定过状态位置的介质，在换到另一台机器时应当保留该选择；而已安装产品的选择应当与它的安装记录放在一起。

## 后果

启动器为 94 MB 且不需要 sidecar；一份发行版中的两个可执行入口——`Launcher.exe` 与打包 Runtime——各由一条命令产出，并共用同一个目标固定值。启动器自身的界面文案是一份由类型检查保证完整的双语字典，因此新消息不可能只出现在一种语言里。

免安装与已安装模式只在一处不同，即 `resolveLaunchRoots`；而这个差异在界面上可见：表头始终打印下次启动将使用的状态目录与工作目录。运行路径上没有其他地方按模式分支。

状态目录规则比“目录必须可写”更严格。想让状态紧挨程序放在介质上的买家，必须放进 `PortableData/` 之下；安装产品的买家根本不能把状态放进程序目录。两种拒绝都会用用户的语言报告，并说明使用了哪个回退位置。

`PKG_NATIVE_CACHE_PATH` 重定向把启动器与一个载体变量耦合在一起。如果后续载体改名，解包会悄悄回到操作者的配置文件；因此验收样机持续测量“介质之外”的清单，并把非空结果当作发现而不是警告。

`Docs/zh-CN/` 与 `Licenses/` 会被呈现，但不在这里生产；中文指南在销售前编写，本工作区中的占位内容只用于跑通这两个菜单项。
